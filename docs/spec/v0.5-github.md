# Spec: GitHub integration (v0.5)

Status: APPROVED by Owner 2026-10-10 (all 5 decisions as recommended). Covers issue #7.

## Goal

After v0.5, anyone looking at the GitHub repository can check, without trusting the development server:

> The trusted checker validates publish attestations and gate receipts against pinned public keys. When the verification workflow runs unchanged, invalid evidence produces a red check. PR verification in v0.5 is advisory; it does not enforce the integrity of the workflow itself (Amendment 2).

## Why the Owner attestation is the anchor

The development server is where agents run. In cooperative mode they run as root, so any key on that server can be read by an agent. A signature made on the server proves nothing about the Owner. The only key an agent can never reach is one that never leaves the Owner's machine. So the root of trust on GitHub is a signature made **on the Mac, at publish time**.

## 1. Publish attestation (Owner, on the Mac)

The publish script, before `git push`, creates a signed attestation for the exact push:

```json
{"kind":"publish","schema":1,"repo":"HlinorAI/hlinor-agent-gates",
 "old_main":"<sha on GitHub before the push>","new_main":"<sha being pushed>",
 "commits":["<first-parent shas old..new, oldest first>"],
 "created_at":"…","tool_version":"0.5.0","signature":"<ssh -Y sign armor>"}
```

- Signed with `ssh-keygen -Y sign -n agent-gates-publish` using a key that lives only on the Owner's machine (ssh-agent or a file outside any agent's reach).
- Stored as a git note on `new_main` in `refs/notes/agent-gates-publish` and pushed atomically with `main` (`git push --atomic origin main refs/notes/agent-gates-publish`).
- Command: `agent-gates publish attest <old> <new> --key <path>`; the v0.5 publish script calls it, shows the commit list, asks `y`.

## 2. Receipts travel with the merge (gate, on the server)

`agent-gates merge` (cooperative and enforced) writes one note on the merge commit in `refs/notes/agent-gates`: the canonical bytes of the verification, acceptance and merge receipts. The publish script fetches these notes from the server and pushes them with `main`. No receipt content changes.

## 3. GitHub Action `agent-gates/verify`

Runs on every push to `main` and on every pull request into `main`. Stdlib Python, no network except the GitHub checkout. Steps:

1. Publish trust anchor = repository variable `AGENT_GATES_OWNER_KEY` (Mac Owner public key). It is read from repo settings, **never from the commit being checked**, so a push cannot replace the key it is checked against. Missing variable on a push → fail. PR receipt signatures use `AGENT_GATES_ACCEPT_KEYS`, not the publish key (Amendment 1).
2. Push to `main`: fetch both note refs. The pushed `after` sha must have a publish attestation whose signature verifies against the anchor, whose `new_main` equals `after`, whose `old_main` equals the event's `before`, and whose `commits` equal `git rev-list --first-parent --reverse before..after`. Any mismatch → fail.
3. For every first-parent commit in the range that is a gate merge (message starts with `agent-gates merge`), its receipt note must check out exactly as `agent-gates merge` checks it: hashes and ids, verifier ≠ author, acceptance signature valid against a key in repository variable `AGENT_GATES_ACCEPT_KEYS` (see Amendment 1), merge commit tree = `merge_tree`, parents = `base_sha`, `head_sha`, acceptance not reused anywhere in the range, merge `created_at` ≤ acceptance `expires_at`. Enforced-mode receipts must also carry a valid gate signature; cooperative ones are shown as `UNSIGNED VERIFICATION`, not failed.
4. Pull request into `main`: the PR head must be a gate merge commit whose `base_sha` equals the PR base, with a valid receipt note (step 3) pushed alongside. Otherwise the trusted checker fails. This is an advisory result, not proof that a non-admin cannot bypass receipt validation by editing the PR workflow (Amendment 2).
5. Output: check summary table (commit, kind, author, verifier, tests summary, acceptance id, result) and the receipt bundle as a workflow artifact (90 days).

## 4. `agent-gates github protect`

Run by the Owner with `gh` authenticated as an admin. Idempotent. Sets on `main`: required checks = existing CI jobs + `agent-gates/verify`; no force push; no deletion; sets the repository variable from `--owner-key <pub>`. Prints the resulting protection JSON. Refuses if the variable already holds a different key (`OWNER_KEY_CHANGED`; rotation is a separate, explicit `--rotate` with the old key's signature).

## Honest limits

- GitHub cannot reject an **admin's** push by content. For the Owner's own pushes the check is detection: a red `agent-gates/verify` on `main` within minutes. Branch protection restricts non-admin direct pushes. PR receipt checks are advisory: required-check names do not pin the workflow implementation (Amendment 2).
- Detection needs someone to look: the Action also opens (or updates) one issue titled `agent-gates: main is unverified` only after a failed push to `main`; PR failures are excluded (Owner review correction). Notifications beyond that are v0.6.
- The Owner key on the Mac is the single point of trust. Losing it means rotating via `--rotate`; leaking it means anyone can attest.

Tests run the Action's script locally against fixture repos (no GitHub calls); one end-to-end run on a scratch repository is done manually by the Owner before release.

## Amendment 1 (Owner, 2026-10-10): two pinned keys

Found in review of phase A: acceptances are signed **on the server** (`accept` runs there), with the server-side Owner key; the publish attestation is signed **on the Mac**. They are different keys by design — the Mac key must never be on the server. So the Action pins two repository variables, both read from settings, never from Git:

- `AGENT_GATES_OWNER_KEY` — the Mac publish key. Root of trust for every push to `main`.
- `AGENT_GATES_ACCEPT_KEYS` — one or more public keys (one per line) allowed to sign acceptances: the server-side Owner key of each project, and optionally the Mac key. Missing variable while the range contains a gate merge → fail.

A server key can be read by agents running as root, so an acceptance signature proves less than the publish attestation; it binds receipts to a known key, and the publish attestation remains the anchor. Tests must use **different** keys for publish and acceptance.

## Amendment 2 (Owner, 2026-10-10): PR verification is advisory

Owner chose to keep v0.5 advisory for PRs and explicitly narrow its guarantee.
A pull_request workflow is read from the PR merge commit: an author can replace
its steps while keeping the required check name. Loading the checker from the
base commit does not pin the workflow that invokes it. Required checks alone
therefore do not guarantee that every non-admin PR was validated against receipts.

- Keep receipt validation and the existing required check, but describe PR results as advisory.
- The Owner must review workflow/checker changes; workflow integrity is a policy boundary in v0.5.
- Main-push detection and issue notification depend on the verification workflow remaining enabled and unchanged. This limitation does not change the cryptographic validation performed by an independently trusted checker.
- Enforcing a separately trusted workflow/ruleset is outside v0.5; no such repository settings are configured here.
- This amendment supersedes the PR blocking claim in step 3.4, test 8 and Owner decision 3; tests 8/9 still exercise the trusted checker locally.

## Out of scope

- GitHub Enterprise pre-receive hooks.
- Signing receipts on GitHub's side (Sigstore / attestations API).
- Notifications other than the single issue (v0.6).

## Owner decisions (2026-10-10, all approved)

1. **Root of trust = Owner signature made on the Mac at publish time**, public key pinned in a GitHub repo variable, not in the repo. Approved.
2. **Receipts and attestations travel as git notes** pushed atomically with `main` (no receipt files committed to the tree). Approved.
3. **Admin pushes are detected, not blocked** (GitHub limitation); non-admin direct pushes use branch protection; PR verification is advisory per Amendment 2. Approved as amended.
4. **Cooperative receipts without a gate signature are reported, not failed**; enforced receipts must be signed. Approved.
5. **The publish script gains one step**: shows the commit list, signs with the Mac key, pushes `main` + notes atomically. Approved.
